## Authority
Follow `AGENTS.md`, `docs/PRD.md` §14 and §16, ADRs 0012 and 0015, `docs/SECURITY.md`, `docs/PRIVACY_ENGINEERING.md` and the threat model. Read the latest handoff. This prompt scopes the current implementation; the PRD remains authoritative.

## Scope (once approved)
- **Product flavors** `play`, `bazaar` and `myket` (only the channels the owner approves).
- **Billing adapters** behind the existing `core:billing` boundary: Cafe Bazaar (Poolakey) and/or Myket IAB. The backend verifies purchases server-side per store and maps them to the existing entitlement model. Prices come from the backend; nothing is hard-coded.
- **Phone-number OTP sign-in** as an *optional* identity method alongside existing ones. The SMS provider sits behind an interface. Requirements: rate limiting, hashed OTPs, replay protection, a lockout policy, and no phone numbers in logs or analytics. Guest-first stays the default.
- Store-specific release builds and signing configuration, plus a store-listing assets checklist.
- Threat-model update for OTP and per-store purchase verification.

## Execution rules
- Implement **M20 only**, and only after the gate is cleared.
- **Store SDK isolation:** Poolakey and Myket SDKs are declared only on their own flavor configurations (e.g. `bazaarImplementation`, `myketImplementation`). The `play` build must not contain them; add a dependency-report check that fails CI if they appear.
- **Secrets:** store public keys, verification credentials and SMS provider credentials are **secrets only** (Cloud Agent secrets / CI secrets). Commit names/placeholders only in `.env.example`; nothing in code, Gradle files or OpenAPI examples.
- Guest/offline use must remain fully functional in every flavor.
- Keep OpenAPI and implementation in sync; additive migrations only.
- Run relevant format, lint, static analysis, unit/integration tests and builds before completion.

## Out of scope
- Expert consultation (M21).
- Changing entitlement rules or what is free vs premium.
- Direct-APK self-update mechanisms.

## Acceptance criteria
- Gate evidence (owner decisions) is linked in the handoff.
- Contract tests for each store verifier using recorded, credential-free fixtures.
- OTP tests: rate limit, lockout, replay rejection, expiry, and no phone number in logs (log-capture test).
- CI fails if a store SDK appears in the `play` runtime classpath (verified by a deliberate negative test or documented check).
- Flavor builds pass in CI. **CI cost note:** a full 3-flavour × (debug, release) matrix roughly triples Android job time. The handoff records the chosen strategy, e.g. `play` on every PR and all flavours on `master`/nightly, with Gradle caching.
- `scripts/security_checklist.py` passes; threat model updated.
- All existing checks pass.
